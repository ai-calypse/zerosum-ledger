CANONICAL FORM (D02-6, version 1)
  Specified in ChangelogHasher and used by both apply and verification; there is no second implementation.
  SHA-256 over, in fixed order: form version (1 byte); previous-hash presence byte (0 for an entity's first row,
  else 1 followed by 32 bytes); entity ID (4-byte big-endian length + UTF-8); seq (8 bytes BE); order ID (16 bytes,
  most significant half first); account code and currency (each length-prefixed); delta and balance_after (each
  8 bytes BE two's complement). recorded_at is excluded: hashing it would force a read-back of the database-assigned
  value inside the apply transaction and fixes no audit fact the other fields do not.

FINDING - the reorder case corrected an expectation, not the code.
  The first run failed with "expected: <HASH_MISMATCH> but was: <BROKEN_LINK>"; the first-bad-sequence assertion
  passed. Swapping rows 2 and 3 leaves the row now claiming seq 2 holding the old row 3's previous-hash, and the
  verifier reads that link before it recomputes the hash, so the swap surfaces as a broken link at the same sequence
  number. The verifier was right and the test expectation was wrong. D02-6 now fixes the per-row check order
  (sequence, form version, link, hash) so the reported failure class is part of the contract rather than incidental.
