--------------------------------------------------------------------------------------------------
DEFECT 1 - accounts were provisioned before the entity lock was taken (ADR-0005 decision point 3)
--------------------------------------------------------------------------------------------------
First run of the harness, pr size, before any fix. The test passed its data assertions, but reported
deadlock retries, which the step document treats as a lock-ordering defect even when assertions pass:

  batched-25  durationMs=9794  samples=353  deadlockRetries=14  lockTimeoutRetries=3  seed=5699988079246323783
  per-order   durationMs=5951  samples=228  deadlockRetries=3   lockTimeoutRetries=6  seed=-6534429403456541701

Root cause: accounts.entity_id REFERENCES entities (D02-1), so inserting an account takes FOR KEY SHARE on
its parent entity row. The engine provisioned accounts and only then took FOR UPDATE on the same rows. Two
batches sharing an entity each held FOR KEY SHARE and each waited for the other's FOR UPDATE. That is a
lock-strength upgrade, which no sort order can prevent; sorted locking only removes ordering cycles.

Fix: provision entities, take the FOR UPDATE lock, then provision accounts (LedgerApplyEngine.applyOrders).

NEGATIVE CONTROL (deliberate revert of the fix, with the zero-deadlock assertion in place):
  broken    batched-25  durationMs=19782  samples=794  deadlockRetries=24  lockTimeoutRetries=7  -> FAILED
            per-order   durationMs=8017   samples=334  deadlockRetries=7                         -> FAILED
            AssertionError: deadlock retries must be zero ... expected: <0> but was: <24>
  restore   LedgerApplyEngine.java sha256 4adc61026f8ff79602b6907eb40ea5d706851a6b1a1991ddc875071cf883a818
            before and after the control: identical
  restored  batched-25 durationMs=558 deadlockRetries=0; per-order durationMs=2032 deadlockRetries=0; BUILD SUCCESSFUL
Both modes fail when the fix is reverted, so the defect is mode-independent and the assertion detects it.

--------------------------------------------------------------------------------------------------
DEFECT 2 - applied_orders rows were inserted in batch order (ADR-0005 decision point 4)
--------------------------------------------------------------------------------------------------
With defect 1 fixed and the zero-deadlock assertion added, the next run still failed, in batched mode only:

  batched-25  durationMs=1377  samples=51  deadlockRetries=1  -> FAILED
              AssertionError: deadlock retries must be zero ... expected: <0> but was: <1>
  per-order   durationMs=1982  samples=90  deadlockRetries=0  -> passed
  (35 tests completed, 1 failed)

This run is itself the negative control for defect 2: the assertion was already in place, the sort was not.

Root cause: INSERT ... ON CONFLICT DO NOTHING makes a concurrent transaction wait on the speculative insert,
so it is a lock. applied_orders rows were inserted in batch input order, so two batches carrying the same
order IDs in opposite order waited on each other. The harness submits the same order concurrently from two
threads, which is exactly that case. Per-order mode issues one insert per transaction and cannot form a cycle,
which is why only batched mode failed.

Fix: insert applied_orders in ascending order_id order (LedgerStore.insertAppliedOrders).
