THE FOUR PINNED CANONICALIZATION VECTORS (D03-3)
  Reordered metadata keys      same hash. Whitespace and 2000 vs 2000.0 also give the same hash.
  Absent vs null vs {}         same hash: all three normalize to one representation.
  Reordered entries            DIFFERENT hash: entry order is significant, because line numbers are part of the order.
  Version tag                  Asserted structurally, not by inspecting a digest: canonicalBytes(order, version)[0] is
                               the form version, the same request under versions 1 and 2 produces different bytes of
                               equal length, and hash(order) is exactly the SHA-256 of those bytes.
  A sixth vector asserts every client-supplied input (source system, key, type, group, adjusts id, metadata, effective
  time) changes the digest, which is what catches a field being dropped from the form.

WHAT ELSE THE ASSERTIONS COVER
  Replay identity   A replay returns the ORIGINAL order_id, created_at and entries, which is what makes
                    database-assigned identifiers the right choice (D03-1): the store never mints an id it would
                    discard on conflict.
  Key reuse         The same key with a different body returns KEY_REUSED and no order, leaving one row.
  Two principals    The same key from trip-simulator and instrument-service creates two orders: uniqueness is scoped
                    by source system.
  First writer rolls back  A holder takes the key in its own transaction and rolls back; the waiter then CREATES and
                    writes its own entries. The rollback here is explicit rather than caused by the deferred zero-sum
                    trigger, because that trigger is S03-T02's and does not exist yet. This exercises the waiting
                    path, not the trigger path.
  Adjustments       An unknown adjusts_order_id raises UnknownAdjustedOrderException (M2 (c)); one that exists but sits
                    in another order group raises AdjustmentGroupMismatchException (§0.3 C2) - a distinct error rather
                    than a constraint violation surfacing as a 500. Neither writes a row.
  Flyway            validate() passes, re-running migrations executes 0, and the applied versions are exactly 1 then 2.

NOT COVERED HERE
  The deferred zero-sum trigger and the append-only triggers are S03-T02. Until they exist, an unbalanced order
  inserted directly by the owner would not be rejected at COMMIT, and the owner can still mutate rows: the migration
  narrows the RUNTIME role's privileges only.
